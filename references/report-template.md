# 代码质量检测报告模板

按以下结构输出 Markdown 报告，保存为 `<项目名>_代码质量报告.md`。

```markdown
# 代码质量检测报告：<项目/目录名>

**检测时间**：YYYY-MM-DD ｜ **代码规模**：X 个文件 / Y 行 ｜ **主要语言**：...

## 总体评分

| 维度 | 得分 | 权重 | 加权得分 |
|------|------|------|---------|
| 正确性与可靠性 | /30 | 30% | |
| 安全性 | /25 | 25% | |
| 可维护性 | /25 | 25% | |
| 风格与一致性 | /10 | 10% | |
| 工程化 | /10 | 10% | |
| **总分** | | | **XX / 100（评级 X）** |

**一句话结论**：<整体评价与最紧迫的风险>

## 问题清单

按严重度分组，每条包含：文件:行号、问题描述、影响、修复建议。

### 🔴 严重 (N 个)
1. `path/to/file.py:42` — <问题描述>
   - 影响：<为什么严重>
   - 建议：<具体修复方式，必要时附代码片段>

### 🟠 重要 (N 个)
...

### 🟡 一般 (N 个)
...（同类问题可合并为一条，列出计数和代表位置）

### 🔵 提示
...（可选优化项）

## 工具检测结果摘要

| 工具 | 状态 | 发现数 | 关键发现 |
|------|------|--------|---------|
| ruff | 已运行 | 23 | 未使用 import ×12、... |
| eslint | 未安装 | - | 建议安装后复测 |

## 亮点

<值得肯定的实践，2-4 条，避免只有批评>

## 改进路线图

1. **立即修复**：安全漏洞、必现 bug（列出具体项）
2. **短期**：重要问题（预计涉及文件）
3. **长期**：重构与工程化建议
```

## 输出要求

- 每条问题必须能定位到 `文件:行号`，不允许泛泛而谈。
- 修复建议要具体可执行，严重问题给出示例代码。
- 报告长度与代码规模匹配：小项目精简，大项目可合并同类项。
- 若某些工具缺失导致检测不完整，在"工具检测结果摘要"中明示，并说明对评分置信度的影响。
